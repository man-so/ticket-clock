# Ticket Clock Phase 2 Engine

## Architecture

Phase 2 implements the core engine only:

```text
Provider Registry
-> Server Time API
-> Sampling
-> Offset Estimator
-> Clock Engine
-> Countdown Engine
```

No Stitch UI, final countdown UI, SEO, login, database, alerts, or deployment work is included in this phase.

## Provider Registry

Providers are centrally allowlisted in `lib/providers/registry.ts`.

The public API accepts only a provider ID:

```text
GET /api/time/[provider]
```

It does not accept arbitrary URLs. Do not add an endpoint shaped like:

```text
/api/time?url=https://example.com
```

Current providers:

- `interpark` -> `https://ticket.interpark.com/`
- `yes24` -> `https://ticket.yes24.com/`
- `ticketlink` -> `https://www.ticketlink.co.kr/`
- `melon` -> `https://ticket.melon.com/`
- `weverse` -> `https://ticket.weverse.io/`

## Sampling

`lib/sync/sampling.ts` collects multiple HTTP samples. Each valid sample contains:

```typescript
type TimeSample = {
  serverDateMs: number;
  requestStartedAtMs: number;
  responseReceivedAtMs: number;
  rttMs: number;
  midpointMs: number;
  offsetMs: number;
};
```

Elapsed request time uses a monotonic clock. The `Date` response header is parsed as the remote server/edge time.

Important limitation: HTTP `Date` is second precision. Millisecond values in `serverDateMs` are derived from JavaScript timestamp representation and are not proof that the provider exposed true millisecond server time.

## Offset Estimator

The estimator flow is:

```text
samples
-> remove invalid samples
-> filter RTT outliers
-> calculate median offset
-> classify sync quality
```

Policies live in `lib/sync/policy.ts`:

- sampling defaults
- RTT outlier filtering
- sync quality thresholds

The quality states are:

```typescript
type SyncQuality = "good" | "unstable" | "failed";
```

`good` means enough samples survived filtering and the RTT/failure/spread thresholds were acceptable. It does not mean exact provider milliseconds.

## Clock Engine

The Clock Engine is independent from React.

It does not keep calling the ticket provider to draw every tick. A sync result creates a reference:

```text
estimated server reference time
+ monotonic elapsed time
= current estimated server time
```

This makes the engine resilient to browser timer throttling. After a background/foreground transition, UI code should call the engine with the current monotonic time instead of trusting accumulated interval ticks.

Re-sync is supported structurally by comparing the old offset with the new offset. Phase 2 records this delta but does not implement complex smoothing.

## Milliseconds Meaning

Future UI may display a value like:

```text
19:56:32.572
```

The `.572` portion means display precision generated by monotonic elapsed time since the last estimated server-time reference.

It does not mean:

- exact server milliseconds
- 1ms accurate
- NTP synchronized
- atomic clock synchronized
- KRISS synchronized

Ticket Clock should describe this as an estimated provider clock, not an exact provider clock.

## Countdown Engine

Countdown is calculated independently:

```typescript
remainingMs = targetTimestampMs - estimatedServerNowMs;
```

It never uses cumulative decrement logic such as:

```typescript
remaining -= 10;
```

The engine always recomputes from the current estimated server time.

## Target Time Policy

The MVP timezone is `Asia/Seoul`.

For date-less `HH:mm:ss` input, the policy is:

- Use today's Asia/Seoul date when the target time is now or in the future.
- Use the next Asia/Seoul day when the target time has already passed.

This makes `23:59 -> 00:00` resolve to the next minute, not to the previous midnight.
